## 1. Identity

**Object Name:** Invoice

**Namespace:** Billing

**Parent Object:** None — top-level object.

**ID Prefix:** INV

**Description:**
An Invoice is the Marketplace's own record of a client-facing billing document generated by SoftwareOne's Navision (NAV) ERP system, synchronized into the platform one-to-one with the NAV invoice it mirrors. It exists to give the Client and Operations Actors visibility of ERP-issued invoices inside the Marketplace, and — through its child Invoice Attachment — to make the official invoice PDF available for download. An Invoice is created and kept current exclusively by the platform's ERP synchronization; no Actor creates or edits one directly through ordinary API usage, and it is typically, though not exclusively, linked to the [[Statement]] that produced it.

**Also Known As:**
NAV invoice; ERP invoice. Distinct from the [[Credit Memo]] (the negative-amount counterpart used for refunds/credits) and the [[Invoice Attachment]] (its child file record).

## 2. Ownership & Visibility

| Actor      | Can Create | Can Read | Can Update | Can Delete | Notes |
| --- | --- | --- | --- | --- | --- |
| Vendor     | No | No | No | No | The endpoint's access policy excludes the Vendor Actor entirely — a Vendor token is refused before any action executes (confirmed via a live PROD fetch: HTTP 403). |
| Operations | Yes (ERP sync only) | Yes | Yes (ERP sync only) | No | The only Actor permitted to write an Invoice, and only through a single bulk endpoint that behaves as an upsert — the same call both provisions a new Invoice and updates an existing one, keyed by the ERP document. See BR-001/BR-002. No delete endpoint exists. |
| Client     | No | Yes | No | No | Read-only — every write path is Operations-only (BR-001). |

## 3. State Machine

This object has no state machine of its own. Its `status` field (Issued, Paid, Overdue) mirrors the status of the underlying NAV invoice and is written by the platform's ERP synchronization exactly like every other Invoice field — there is no dedicated transition endpoint for any status value, and the platform does not itself enforce a permitted sequence between the three values (see BR-014). Availability of the Invoice record is instead controlled by the ERP synchronization process described in Section 4: an Invoice comes into existence, and is kept current, only as a byproduct of that sync.

## 4. Business Rules

| Rule ID | Rule Statement | Applies In State(s) | Actor Scope | Notes |
| --- | --- | --- | --- | --- |
| BR-001 | An Invoice can only be written through a single Operations-only bulk endpoint that behaves as an upsert; there is no separate API to create or update an individual Invoice, and no Vendor or Client write path exists at all. | N/A | Operations | The endpoint requires bulk-upsert and async request headers and processes items asynchronously. |
| BR-002 | An Invoice's identity is deterministic: the first sync for a given ERP document number and country code pair provisions its identifier, and every subsequent sync for the same pair resolves to that same Invoice rather than creating a new one. | N/A | Operations | The (document number, country code) pair is effectively the Invoice's natural key. |
| BR-003 | A resync whose incoming ERP revision is not strictly newer than the Invoice's currently stored ERP revision is skipped, leaving the Invoice unchanged. | N/A | Operations | Guards against an out-of-order or delayed sync overwriting newer data. See Section 9. |
| BR-004 | Reading an Invoice is permitted to the Client and Operations Actors; the Vendor Actor is refused entirely. | N/A | All | A Vendor request is refused outright, not merely field-suppressed. |
| BR-005 | Sell-side purchase pricing (markup, margin, total purchase price, and the equivalent per-line purchase-price and sales-markup/margin fields) is visible only to the Operations Actor; the Client Actor sees only the sale-side totals and per-line sale amounts. | N/A | All | Reference preamble §6.3. |
| BR-006 | An Invoice's linked [[Statement]] is resolved by matching the ERP sales order number carried in the sync payload against the Statement's own ERP identifier — not by directly consuming the Invoice's own separately-supplied statement-identifier field. | N/A | System | If no match is found, the Invoice is stored with no Statement link and no error is raised. See Section 9. |
| BR-007 | An Invoice's billing type is derived from its matched Statement's own billing type when a Statement link is resolved (BR-006); when none is resolved it defaults to Manual. The field cannot be set directly by the sync payload. | N/A | System | Values: Automated, Manual, Consolidated. |
| BR-008 | The Agreement reference is taken from the sync payload's own agreement identifier when supplied in the expected format; if the Invoice is also linked to a Statement that itself carries an Agreement, that Statement's Agreement supersedes it. | N/A | System | — |
| BR-009 | The Buyer (and, through it, the Client Account) is resolved by matching the sync payload's customer identifier against the Buyer's own ERP customer identifier. | N/A | System | A sync for a Buyer that cannot yet be resolved is skipped rather than failing the wider sync batch — see Section 9. |
| BR-010 | The Seller is resolved by matching the sync payload's country code against the Seller's own external identifier. | N/A | System | Unlike a missing Buyer, a Seller that cannot be resolved fails the sync task outright — see Section 9. |
| BR-011 | The `attributes` field is a read-only projection of a fixed subset of the Invoice's own ERP data (quote number, order number, your-reference, external document numbers, due/posting/document dates), recomputed by the platform on every sync rather than independently settable. | N/A | System | — |
| BR-012 | The Invoice's own generated PDF is attached automatically as an output-type child attachment the first time it is synced. | N/A | System | Not created for an Invoice whose resolved Seller is flagged as a legacy migration case, in which the PDF is sourced differently. |
| BR-013 | An Invoice has no delete endpoint and cannot be removed by any Actor via the API. | N/A | Operations | See Section 8. |
| BR-014 | No sequence between the `status` values Issued, Paid, and Overdue is enforced by the platform; any value may be written by any subsequent sync regardless of the current value. | N/A | System | A fourth accepted value, `Generated`, shares the same underlying value as `Issued` and is retained only for backward compatibility — it is not produced by the platform's current ERP synchronization. |

## 8. Reversibility & Data Retention

**Reversible transitions:**
This object has no state machine (Section 3). Its `status` field can be rewritten to any of Issued, Paid, or Overdue by a subsequent ERP resync — the platform enforces no permitted sequence between them (BR-014).

**Deletion:**
An Invoice cannot be deleted in any state. There is no delete endpoint for it in the API (BR-013).

**Audit & history requirements:**
An Invoice records a created and updated event plus a per-status event history (issued/paid/overdue, each with timestamp and Actor). Unlike some other Billing objects, this `audit` object is included in the API response by default. Every sync that changes `status` also publishes a status-changed event to the platform notification bus, with the linked Client Account granted visibility of that event. Price, line, and ERP-data values are replaced wholesale on each sync; prior values are not retained beyond the audit event trail.

## 9. Failure Modes & Edge Cases

| Scenario | Expected System Behavior | Actor Impacted | Risk Level | Notes |
| --- | --- | --- | --- | --- |
| The ERP sales order number in a sync payload does not match any known [[Statement]] | The Invoice is saved with no Statement link and a default Manual billing type; no error is surfaced to any Actor. | Operations, Client | Medium | See BR-006. Only Operations investigating the Invoice directly would notice the missing link. |
| The Buyer cannot be resolved from a sync payload's customer identifier | The sync task for that Invoice is skipped without failing the wider sync batch — treated as a success. | Operations | Low | Buyer data may sync on its own cadence; a temporary miss is expected to self-heal on a later resync. See BR-009. |
| The Seller cannot be resolved from a sync payload's country code | The sync task fails outright, unlike a missing Buyer. | Operations | Medium | See BR-010. |
| A resync arrives with an ERP revision no newer than the Invoice's currently stored one | The resync is silently skipped, so a legitimate but delayed or out-of-order update is never applied. | Operations | Low | See BR-003. |
| The Vendor Actor attempts to read or manage an Invoice | The request is refused entirely. | Vendor | Low | See BR-004. |
